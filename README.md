# I-Mage

Локальный поиск по личной фототеке: **по смыслу**, **по объектам** и **по человеку**.

Фото не уходят в облако. Модели крутятся на вашей машине, индекс живёт рядом с файлами. Запрос вроде «закат с airplane над горами» ищется сразу в двух пространствах: CLIP понимает сцену, YOLO поднимает снимки, на которых самолёт реально детектирован.

Это pet-проект, не продукт с пользователями. Цель — собрать **production-minded ML-систему**: не ноутбук с эмбеддингами, а сервис с каталогом, инкрементальной индексацией, векторным поиском и разделением GPU между фоном и интерактивом.

---

## Зачем это нужно

Личная медиатека растёт быстрее, чем человек успевает её раскладывать. Папки, даты и имена файлов почти ничего не говорят о содержимом. Облачные фотосервисы решают это ценой приватности и привязки к вендору.

I-Mage закрывает три реальных сценария поиска:

| Намерение | Пример | Как ищется |
|-----------|--------|------------|
| «Как выглядело» | закат на море, кот на диване | CLIP: текст и фото в одном векторном пространстве |
| «Что на снимке» | car, dog, airplane | YOLO: классы COCO в SQLite, фильтр без прогона модели |
| «Кто на снимке» | фото человека с телефона | ArcFace: эмбеддинг лица → похожие кадры + кластеры людей |

Гибридный запрос объединяет первые два: снимок, который и семантически близок, и содержит названный объект, ранжируется выше.

Для ML-инженера это тот класс задач, который встречается в поиске, модерации, цифровых архивах и on-prem CV: несколько моделей, разные гранулярности результата (фото / объект / лицо), индекс, который нельзя пересчитывать с нуля, и интерактив, который не должен ждать фоновый батч.

---

## Что умеет сейчас

- Семантический поиск по текстовому описанию (CLIP → Qdrant).
- Поиск по объектам COCO и подсветка классов в запросе.
- Поиск человека по загруженному фото (InsightFace / ArcFace).
- Автоматическая группировка лиц в «людей» (DBSCAN по косинусу) с ручными правками: имя, слияние, разбиение. Перегруппировка не затирает ручные назначения.
- Фоновая и ручная индексация по модулям (`clip` / `yolo` / `faces`), сверка каталога с диском, дозаполнение дыр.
- Веб-UI и FastAPI; стриминг прогресса поиска (NDJSON).

Не входит в текущий scope: видео, поиск картинка-по-картинке как отдельный продукт, упаковка в desktop-приложение, мультипользовательский режим и авторизация.

## Архитектура

Поиск **читает** уже построенный индекс. Индексация **пишет** его отдельно. На поисковый запрос модели нужны только чтобы закодировать query (текст или лицо), а не чтобы заново прогнать всю библиотеку.

```text
диск с фото
    │  scan + SHA256
    ▼
 SQLite                          Qdrant
 каталог, YOLO, лица, люди       CLIP-векторы фото
 статусы модулей, index_runs     ArcFace-векторы лиц
    ▲                                  ▲
    │            IndexExecutor         │
    └──────── GPU scheduler ───────────┘
              CLIP / YOLO / ArcFace
                       ▲
                       │ read
                  FastAPI + UI
              /search  /people  /index
```

**Почему два хранилища.** Структурированные факты (класс, bbox, статус модуля, человек) удобны в SQL. Эмбеддинги — в векторной БД. CLIP и ArcFace дают векторы одной размерности (512), но это **разные пространства**, поэтому две коллекции Qdrant: `context` (одно фото — один point) и `faces` (N лиц на фото). YOLO в Qdrant не кладётся.

**Идентичность файла — содержимое, не путь.** `image_id` стабилен; SHA256 решает, нужна ли переиндексация; `mtime`/`size` — только быстрый pre-check. Переименование не сжигает эмбеддинги. Upsert в Qdrant идёт с детерминированными point id — повторный job безопасен.

**Один GPU на три модели.** Индексатор берёт устройство на ограниченный батч. Поисковый запрос идёт с более высоким приоритетом и вклинивается между батчами, а не встаёт в конец очереди на часы.

```text
ml/          протоколы моделей + реализации + сервисы поиска
indexing/    scan, gap, батчи, clustering, GPU scheduler, executor
db/          SQLAlchemy, SQLite WAL
vectors/     клиент Qdrant
api/         FastAPI: search, people, index, settings
clients/     веб-UI и тонкий CLI над HTTP
tests/       фейки моделей, API, гонки, опционально реальные веса
```

## ML

Три независимых бэкенда за абстракциями `EmbeddingModel`, `ObjectsRetriever`, `FaceRecognizer`. Тесты ходят в фейки той же формы; смена модели не должна ломать API.

### Семантика — CLIP

- Модель: `openai/clip-vit-base-patch32` (Hugging Face `transformers`).
- Текст и изображение в одном пространстве; L2-нормализация, косинус в Qdrant.
- Батч `encode_images`; размер батча задаётся (`CLIP_BATCH_SIZE`, по умолчанию 32).
- CUDA, если доступна, иначе CPU. Старт предпочитает локальный HF-кэш, чтобы не зависать на Hub.

Это сознательный baseline: достаточно сильный для личной библиотеки, относительно лёгкий, чтобы держать на одной потребительской GPU вместе с детектором и лицом.

### Объекты — YOLOv8s

- Ultralytics, веса `artifacts/yolov8s.pt`, порог 0.25, IoU 0.45.
- 80 классов COCO пишутся в SQLite (`label`, `confidence`, bbox).
- Поиск по классу — SQL, без повторного инференса.
- В unified-поиске названия классов вытаскиваются из запроса (длинные лейблы вроде `traffic light` имеют приоритет над короткими).

Детектор здесь не «ещё одна нейросеть для демо», а способ получить **фильтруемые факты**, которые CLIP по тексту даёт хуже и дороже.

### Лица — InsightFace `buffalo_l`

- Детекция + ArcFace 512-d, InsightFace `FaceAnalysis`.
- На индексе: все лица фото → метаданные в SQLite, векторы в Qdrant.
- На запросе: лучшее лицо с загруженного снимка → ANN по коллекции `faces` → агрегация до фото (max score), порог сходства.
- Кластеризация: DBSCAN, метрика cosine, `eps = 1 - threshold` (по умолчанию 0.65). Синглтоны не становятся «людьми» — в альбоме человек появляется от двух лиц.
- Human-in-the-loop: rename / merge / split. Источник назначения (`auto` vs ручной) хранится явно, чтобы пересчёт кластеров не откатывал правки пользователя.

Это типичный production-паттерн для identity: модель предлагает группировку, человек её чинит, система это помнит.

### Гибридный ранжир

Unified search сливает CLIP-хиты и YOLO-хиты по пути файла. Снимок, попавший в оба канала, получает бонус. Так «закат с airplane» не тонет среди любых закатов и не сводится к любым самолётам.

## Инженерия вокруг моделей

Имеет значение не только какая сеть, а как она живёт в системе:

- **Инкремент.** Индексируются только дыры: нет строки модуля или статус ≠ `done`. Изменился hash — модуль пересчитывается. Удалённый файл уходит из SQLite и из Qdrant.
- **Частичный отказ.** CLIP может быть `done`, faces — `failed`; ретрай точечный, не всего каталога.
- **Порядок записи.** Сначала store, потом `status=done`. Upsert идемпотентен — обрыв посередине не плодит дубли.
- **Каталог и индекс разведены.** Сверка файлов на диске не гоняет GPU. Поиск не запускает индексацию «на всякий случай».
- **Конкуренция.** SQLite в WAL, `busy_timeout`, локи на модуль индексации, кооперативная остановка скана при shutdown.
- **Наблюдаемость.** `index_runs` с фазой и прогрессом; `/health` отдельно сообщает, жив ли Qdrant.

Стек сервиса: Python, FastAPI, SQLAlchemy, SQLite, Qdrant, PyTorch. Тесты — pytest: API, поиск, индексатор, гонки и локи, GPU-планировщик, интеграция с Qdrant. Реальные веса — отдельный маркер (`RUN_ML_TESTS=1`), чтобы CI не тянул CUDA.

## Быстрый старт

Нужны conda-окружение `ml-env` (PyTorch, transformers, ultralytics, insightface и зависимости из `requirements.txt`) и Docker для Qdrant.

```bash
docker compose up -d

conda activate ml-env
./run.sh
```

Открыть http://127.0.0.1:8000

Qdrant — только сервер (`QDRANT_URL`, по умолчанию `http://127.0.0.1:6333`). Встроенный файловый режим убран: single-writer лок ломал несколько процессов и `--reload`.

Во время индексации не используйте `uvicorn --reload` — рестарт оборвёт прогон. Для разработки: `./run-dev.sh`.

Каталоги с фото задаются в настройках UI или через `IMAGE_SEARCH_DIR` / `FACE_SEARCH_DIR`. Датасет для семантического поиска: `python scripts/download_data.py`. Для лиц: `python scripts/download_celeba.py`, затем `python scripts/build_small_celeba.py`.

```bash
conda activate ml-env
python -m pytest
```

## Что сознательно не делалось

Отдельные ML-воркеры на процесс, watch файловой системы, обучение своих весов, SaaS и аккаунты. Пока один локальный индекс и одна GPU — это усложнение без выигрыша. Сначала стабильные scan, jobs и планировщик устройства.

План слоёв индекса (SQLite → Qdrant → разделение API/индексатора): [docs/indexing-plan.md](docs/indexing-plan.md).
